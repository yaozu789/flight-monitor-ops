# Flight Monitor: context for Claude Code

Personal cheap-flight radar for Yaozu. It watches SFO/OAK/SJC round trips to destination groups (Phase 1: Japan $500, NYC $250), 3–9 months out, 5–14-day trips, economy, ≤1 stop. It alerts only on **rechecked, under-cap** fares. Honest framing: best-effort sampled coverage, "price rechecked", never "bookable".

## Architecture
- `run.py`: the CLI. `check --scheduled` is the scheduled cycle, and `run_guarded` wraps it with: lock → drain → backoff/slot no-op → fn with run deadline → heartbeat.
- `cmd_check` order: mint cells → drain → retry recheck → leftover verify → `sentinel.collect` → **same-slot verify** → burst triggers → prepare handoffs. Every output, including no-ops and stops, carries `handoff.alerts` for the agent to relay verbatim.
- `transport.py`: wraps curl_cffi `Session.get/post`. It counts every HTTP attempt before sending, fails closed with no guard, forces concurrency to 1, and detects 429/CAPTCHA/blank pages and persists the backoff.
- `budget.py`: `BudgetGuard.reserve()` is atomic (`BEGIN IMMEDIATE`, separate connection). Limits: 150/day (acceptance phase), a per-run allowance, a verify reserve, and category caps. The reserve and caps come from `effective_verify_reserve(watches)` / `effective_category_caps(watches)`: while every watch is `alert_mode: collect` (the `watches.yaml` default), the reserve is 0 and the whole ceiling goes to sentinels (verify/retry/background/burst caps 0). With any alerting watch in a redesign config: reserve 24, sentinel cap = ceiling − 24 − 12, background 0. Only a pure legacy config (all `cap`, no `windows:`) keeps `CATEGORY_CAPS`. `sentinel.daily_headroom()` reads the guard's ceiling and reserve, so pacing matches `reserve()`. `BudgetExhausted` **must stay a BaseException**, or fli wraps and retries it.
- `sentinel.py`: **named windows** (redesign, `docs/redesign-spec.md`): a watch with `windows:` + `nights:` in `watches.yaml` mints every window × every trip length as one union (cells carry `window_name` and `refresh_hours`); `near` uses `step_days` or `weekdays` (e.g. Fridays), with no cap; `depart_hours: {weekday: "HH-HH"}` limits only the **outbound** departure time on that weekday (Saturday morning for weekend trips), passed to fli on the first segment only. `store.due_cells(..., slot=)` orders by overdue ratio (hours since check / refresh target). Collection for named windows checks **only due** sentinels (whole allowance), then bursts only if none of this run's groups still has a due sentinel (`store.overdue_sentinels`), then background. Fresh cells are never re-checked early, so daily use follows the refresh targets (~71/day for Stage A), not the ceiling. A 0-attempt run with nothing due at its start (`overdue_at_start == 0`) is idle, not stalled. Legacy configs keep the old odd/even order. Bursts are clipped to the trigger's window and weekdays (bounds fixed at the day the trigger was queued) and sweep only the watch's `nights`. Legacy watches without `windows:` keep: about 27 fixed departure anchors per group (7-day stays) and a weekly background grid, both on a fixed calendar lattice (`GRID_EPOCH`), so the grid doesn't grow as days pass. Also bursts (60 attempts, resumable) and pacing across the day's runs at `run_every_minutes`. Known limits: changing `trip_length_days` during an active burst can skip or repeat a few of its duration steps, and changing a group's airports reuses its cells' price baselines for drop triggers (72 h window). Bursts expire in 24 h. For short custom windows (over 27 lattice points) the 27-anchor cap keeps the earliest dates, so the far edge is thinner; the default 3–9 month window gives about 26 and is unaffected.
- **Collect-only mode** (`alert_mode: collect`, redesign A2): prices are stored, nothing else. Before the drain, `store.enter_collect_mode` retires the watch's non-terminal outbox rows (health `mode_collect`) and expires its queued/active triggers and burst progress in one transaction. `cmd_check` skips retries, verification, drop triggers and bursts for these watches. Named-window watches have no background grid. Stage A (Japan near+far at 28 nights, NYC near at 7/14) runs this way.
- **Counters and the ramp gate** (redesign A3): every `check_cell` query logs one row to `query_log` (`ok`/`empty`/`transport_fail`/`unparseable`/`error`/`budget_cancel`/`deadline_cancel`/`throttle`, with the daily ceiling it ran under; kept 120 days; the poller sets `poller.LAST_OUTCOME` so a failed fetch is not mistaken for an empty result). `run.py coverage [--days 5]` prints refresh ages per group × window (p50/p95/max hours since the last success; never-succeeded cells count from minting), outcome counts and the unknown rate (budget/throttle cancels are not completed queries), deadline stops and throttled runs, and the gate for the next budget step: ≥ 5 days of history **at the current ceiling**, every configured group × window measured (none missing), 0 throttles, unknown rate < 5%, 0 deadline stops, worst p95 ≤ 1.5 × target.
- `verifier.py`: rechecks the same fingerprint (includes flight numbers and times). Price must be ≤ cap, with **no tolerance**, and there are **no new-low alerts**.
- `outbox.py` + `store.py`: states are `pending → handoff_prepared → relay_attempted_unconfirmed` (scheduler), and `user_confirmed` is human-only via `outbox-confirm`. There is no "sent" state, because Muse push gives no receipt. Each rearm (a new price event in the same week) bumps `event_no`. `outbox-mark` and `outbox-confirm` require `--event`, and every relayed message ends with `Alert: <id> event <n>`, so a late confirmation can't land on a newer deal. Rows that existed before `event_no` was added default to 1; the live outbox was empty when it shipped. At most 2 handoffs, rechecked before a retry. Dedup is per (watch, departure week), re-alerting only on a drop of at least max($15, 5%).
- `weekly.py`: the Monday price report, sent even with no deals. It is built from stored data only (no searches) by the first **scheduled** run at or after Monday 16:00 UTC (9 AM PDT), and rides `handoff.weekly_report` on every output of that run (no-ops and stops included) until `report-mark --week <w>`, at most 2 runs. `weekly-report` previews it. **Named-window watches** (redesign A4) get a per-window digest instead: for each window, the cheapest fare stored this week whose departure is inside the window *now* and whose stay the watch tracks (price, dates, nights, airline, stops, age, `(stale)` past the refresh target), last week's low for that window, and how many departure dates were checked within the refresh target. With every watch collect-only it says alerts are off, and caps appear nowhere (chart cap lines only for `cap` watches).
- `dashboard.py` + `dashboard/` (page, `app.js`, vendored Chart.js libs, strict CSP): the monitoring dashboard (price history, requests per run with stalls, daily spend, problems; 180 days of prices, 14 of runs). The page is static (GitHub Pages of the public `flight-monitor` repo) and holds no data; `dashboard.link()` packs stored data into the URL fragment (`#v1.` + base64url raw-deflate JSON), which browsers never send to the server. `dashboard-link` prints one; the weekly report includes one. The page renders fragment data with `textContent` only (untrusted input).
- Stall detection (`run._stalled`, `store.stall_streak`): a run that sent 0 requests although a full sentinel or background check fit its allowance and cap is `stalled`; 3 back-to-back pings `/fail`. 0 requests with nothing affordable is neutral (neither counts nor breaks the streak).
- `heartbeat.py`: healthchecks.io, pinged only on `--scheduled` runs. Success on a finished cycle, including legitimate no-ops. `/fail` on a crash, a non-zero return, 3 lock losses in a row, or 3 deadline stops in a row. The URL is read from the `HEALTHCHECKS_PING_URL` env var (on Muse: `.env`, mode 600), never logged.
- fli convention: for round trips, **the outbound leg's price is the full round-trip total** (fli's own CLI and tests).
- Itinerary endpoints are each direction's first departure and **final** arrival. Observations written before PR #17 stored the first leg's arrival (the layover) as `destination` for connecting flights, so their fingerprints differ from new rows. They are historical only (the live outbox was empty when this changed). Rechecks query the watch's grouped airports and match the exact fingerprint.

## Rules
- Never commit `data/`, `*.db`, `.env`, tokens, or the ping URL.
- Test fixtures stay inside the repo, with no machine-specific paths.
- **A new test must fail on the code before its fix.** Check this by running the tests against the old file.
- Prefer tests that drive the real `BudgetGuard`/outbox/`run_guarded` paths and assert on printed output. Tests that stubbed both collection and verification missed real bugs.
- Don't send real flight searches from the Mac without Yaozu's OK. Google rate-limits, and the budget exists for a reason.
